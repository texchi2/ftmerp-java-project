# FTM IT 與 SIMIS ERP 的開發實錄
## ——從掙扎中學習，走向自主開發之路

**撰寫：** Dr. 祁力行 Chi Li-Hsing，FTM AI Chief 
**日期：** 2026 年 5 月  

---

## 一、背景

2024 年第四季，FTM Garments Swaziland 與 IISI 正式簽約，引入 SIMIS ERP 系統，目標是將製造流程從銷售訂單（Sales Order）一路串連至物料清單（BOM）與採購訂單（Purchase Order）的自動化生成，並朝 MRP（物料需求計劃）與生產排程邁進。

這是 FTM 在數位轉型道路上的一次重要嘗試。

---

## 二、實戰現場：業務部門與 IT (FTM+SIMIS) 的共同奮鬥

在實際導入過程中，FTM 業務部門與 IT 團隊攜手嘗試，以 SIMIS 系統處理從新銷售訂單到 BOM、再到採購訂單的完整工作流程，SIMIS 開發團隊的認真努力，不可磨滅。

而我們共同遇到情況是：

**完成同樣的業務流程，使用 SIMIS 系統，與使用 Excel 試算表的傳統方式相比，新系統反而花費更多的時間。**

這並非人員不熟悉系統的學習曲線問題，而卡在根本的設計困境：

- **缺乏自動化：** 新系統各模組之間的資料流動，需要大量人工介入與逐步確認，無法自動串接。
- **電腦淪為打字機：** 員工使用系統的方式，輸入資料、存檔、再切換視窗、再輸入。系統提供的，是「另一種輸入方式」，並無法加速流程的進行。
- **MRP 與生產排程尚未開始測試：** 因為流程的前段（銷售訂單→BOM→採購訂單），已讓團隊對新系統失去信心；MRP 與生產排程的整合，始終停留在規劃階段，未能真正落地。基於迫切的須求，FTM 各單位開始委託FTM IT team，開始嚐試開發單項功能。
- **色系與款式的協調，仍需人工逐筆核對：** 成衣製造業最核心的需求之一——款式編號與輔料色系的自動匹配——系統無法處理，只能靠人工對照，錯誤率與工作量雙雙提升。

- **SIMIS 實為 MRP 模組，而非完整 ERP；且並非 FTM 當前最急迫的痛點：**

  嚴格來說，SIMIS 系統的功能定位更接近 MRP（物料需求計劃）模組，而非一套完整的 ERP。然而，MRP 並不是 FTM 目前最迫切的需求——**銷售訂單到製造原料（BOM）的流程串接，才是當下最急需解決的核心瓶頸。** 依SIMIS 既有的架構，hard coding 並未能充份利用關聯性資料庫的特長(雖然使用Borland Database Engine, BDE串接 MS SQL server)。

  這個問題的本質，必須建立在**關聯式資料庫（RDBMS）**的基礎上，才能應付成衣製造業中複雜的資訊流動態關係。在尚未有適當軟體之前，FTM 業務部門已經磨練出人腦與滑鼠方式，藉由 Excel 試算表與紙本資料來處理銷售訂單、跟單（訂單追蹤）、以及 Fabric／Trim 的採購協調——這正是目前最耗時、最容易出錯的環節。

  事實上，FTM 業務部門長期以來，已在無意間建立了一套「人工關聯式資料庫」：她們的試算表已具備部分正規化（2NF、3NF）的表格結構，表格之間透過 Primary Key 與 Foreign Key 建立關聯，而「人工 copy-paste」則扮演了「人腦 SQL query」的角色，而且能夠應付幾乎是一日數變的訂單內容更新。當然這是人員不斷加班與燒腦的結果。

  舉例而言，銷售訂單與拉鍊輔料之間的關係，若以 SQL 表達即為：

  ```sql
  SELECT S.PO, S.SKU, S.quantity,
         Z.color, Z.size, Z.material
  FROM   sale_order S
  INNER JOIN trim_zipper Z ON S.SKU = Z.SKU;
  ```

  這套邏輯，她們早已熟稔——只是用人腦與滑鼠在執行，而非資料庫引擎。**只要在 PostgreSQL 中建立對應的 ERD 與資料庫結構（sale order + BOM），這個瓶頸便有機會由電腦系統來完成。**

  FTM IT 團隊曾設想以自行開發的2025 Web 架構（MERN stack）與 SIMIS MRP 模組對接；然而實際評估後發現，兩套系統的技術世代相差約 25 年，hard coded database schema 讓整合難度遠超預期，最終放棄此路線。

  值得一提的是，FTM 的主要生產模式為 **make-to-order**（依訂單生產），少數屬於 **make-to-minimum stock**（最低庫存生產）。前者要求原物料盡量不落地、存放時間極短，是極度精實的供應鏈管理挑戰——正如 IISI Mr. Jerry 也認同的，這在業界屬於相當高超的執行能力，目前完全靠密集人力支撐。**而有資格成為 FTM 的現代化ERP 系統，必須要能承擔這個艱鉅的任務。**

## 三、從掙扎中萃取的洞見

這段經歷雖然辛苦，卻為 FTM IT 團隊帶來了最真實、最接地氣的 ERP 實務認識。

> 「唯有親身走過這條路，才能真正理解：一套 ERP 系統，必須為製造業務流程服務，而不是讓使用者去配合系統的限制。」

在與各部門同仁的日常深度訪談中（業務、採購、倉儲、生產、產品開發），FTM IT 團隊逐漸釐清了幾個關鍵事實：

1. **語言的距離，是隱形的鴻溝。** 系統開發商在台灣，FTM 在史瓦帝尼；跨越語言與時區的需求溝通，往往使真正的痛點難以被準確捕捉與即時回應。
2. **「一位 IT 搭配一個部門」的模式，才能真正理解需求。** FTM IT 團隊在這段期間發展出一個工作原則：每位開發人員深度配對一個業務部門，以相同的史國母語（sisiwati）直接溝通，理解他們每天真正在做什麼、卡在哪裡、需要什麼。
3. **自動化的前提，是對FTM商業製造邏輯的深度理解。** 沒有捷徑，沒有modules可以跳過這個步驟。

## 四、轉折：FTM IT 走向自主開發

正是這些第一線的掙扎與觀察，促使 FTM IT 團隊在 2025 年底做出了一個重要決定：

**以Apache Tomcat + Java + PostgreSQL + MongoDB + Express.js + React + Node.js (MERN)開源平台為基礎，由 FTM IT 團隊自主開發，量身打造符合成衣製造業務邏輯的 ERP 系統。**

這個轉折點的核心理念是：

- **一位開發者，配對一個部門（one coder, one department）**
- **以相同的母語溝通，而且開發者均有製造流程第一線的工作經驗，有效減少傳譯的失真**
- **每日訪談，持續精進，讓系統跟著實務工作流程走**
- **採用現代化開源 Web 架構（Java / PostgreSQL / REST API），完整呈現 server/clients 的架構，並確保更新以及資訊安全**

截至 2026 年 5 月，FTM IT 團隊已完成多個核心模組的開發與部署，系統正在逐步取代過去依賴試算表的工作環節。
